## 项目一：机器人轨迹精度分析工具与真机复播自动化

### 一句话

把「机器人到底有没有按规划走、慢了多少毫秒」这件事，从人工看波形变成**产出一份可交互报告的自动化流水线**。

### 做了什么

**1. 多层级轨迹精度分析工具（`awr_analysis`，约 1 万行）**

- 打通机器人执行链路的**四层数据源**：离线规划（npz）→ 伺服指令 → 关节指令 → 关节反馈，
  逐跳算出**精度残差**与**时延**
- 设计**时延估计 + 补偿**算法：原始误差中九成以上是伺服滞后，不补偿会把
  「机器人慢了 78 毫秒」误读成「机器人偏了 4 度」—— 后者会让人去查机械，而问题不在那儿
- 用**速度模长相关性**给每个时延估计打分（相关性 < 0.3 时判定「估不出」，
  拒绝补偿而非硬给一个数），避免把噪声拟合成结论
- 处理**录制空洞**与**逐层停发**：不隔断的话，跨空洞的巨型差分会把相关性绑架到 0.03，
  让一次完好的执行被误判成「数据不可用」（实测真值 0.966）
- 产出黑底宽屏、可缩放可 hover 的 HTML 报告（plotly 内嵌，无外链），
  另有一份 ~300KB 的内联 SVG 精简版可发邮件 / 贴 issue
- 编写 **57 个单元测试**钉住算法行为

**2. 真机复播自动化（`awr_autotest`，端到端）**

输入一份同事给的 mock 规划请求，自动走完：

```
拆两个 yaml → 上传真机 → 起录制 → 复播 → 取回 record → 出精度报告
```

**判定口径**：能生成报告 = 成功。不看精度数值（那份报告本就没有验收线）。

- 真机实跑验证：复播轨迹与 mock **残差 RMS 0.093°**（编码器噪声量级），
  证明整条链路没有引入畸变
- 全流程耗时 **331 秒 → 18.4 秒**；运动帧占比 **1.9% → 13.1%**；
  控制层覆盖率 **1.8% → 41.6%**（后两项指标原先看着像「数据源没数据」，
  实为录制被超时拖长导致的稀释）

### 技术点

`Python` · `numpy` · `plotly` · `pytest` · `SSH/SFTP` · `protobuf` · 时序对齐 / 信号处理

## 项目二：测试数据记录服务（`awr_testpillar`）

### 一句话

测试人员在机器人端做线束插接测试，**记录自动落到飞书多维表格**；
Jira 侧的缺陷单**自动关联回填**到对应记录。

### 做了什么

**1. FastAPI 数据记录服务**

- 设计**按设备号 + 测试阶段动态路由**：请求里带设备号与阶段，
  服务实时定位飞书里对应的表（新增设备表无需改代码）
- 抽象飞书多维表格的**复杂字段写入**：单选/多选（含选项自动补齐）、
  日期（毫秒时间戳）、人员（邮箱 → open_id）、URL 等
- 支持**两种存储模式**（新老目录）与**静态映射兜底**，兼容历史数据
- **写入去重**：APP 侧加了两轮重试之后，出现「已写入但返回超时 ⇒ 重复提交」，
  设计按 `日期 + 时间 + 线束号` 的**两层去重**（批内 + 跨请求），
  并且刻意**绕过客户端 5 分钟缓存**（重试发生在几十秒内，用缓存会读到写入前的快照，
  去重形同虚设）

**2. Jira / 飞书项目缺陷单自动回填**

- 拉取缺陷单，按 `设备号 + 线束号 + 时刻（±600 秒容差）` 匹配到飞书里的测试记录，
  把缺陷链接回写到记录行
- 处理幂等（同一单重复投递不重复写）、无匹配时的明确跳过原因
- 支持飞书 webhook 触发与定时任务两种入口

### 技术点

`Python` · `FastAPI` · `飞书开放平台 API`（bitable / wiki） · `Jira REST` · `pytest`
