# 工作经历 · 详细技术分析

**业务背景**：AWR 线束插接机器人（双臂 7+7 自由度 + 腰部 3 + 全向底盘）。
测试人员在产线旁对线束做取料 / 理线 / 插接等工序，需要回答两个问题：

1. **机器人到底有没有按规划走？差多少？慢了多少毫秒？**
2. **测试结果有没有被完整、准确地记录下来？**

对应两个项目：**轨迹精度分析（+ 真机复播自动化）** 与 **测试数据记录服务**。

# 一、轨迹精度报告自动化

## 1.1 要解决的问题

机器人的执行链路是四层的，从「想怎么走」到「实际在哪」：

```
   规划层                控制层                 执行层             执行层
离线 npz ──────────► servo_joint_cmd ──────► joint_states_cmd ──────► joint_states
(attachment/)        /whole_body/…           /joint_states_cmd      /joint_states
   ↑ 计划               ↑ 伺服指令               ↑ 下发指令            ↑ 编码器反馈
```

**关键难点**：这条链路上「误差」和「滞后」是**混在一起**的。原始数字看着很大，
但其中九成以上不是精度问题，是**时间没对齐**。

不把这两者分开，就会得出错误结论 —— 而错误结论会把人引向错误的排查方向。

## 1.2 核心技术：时延估计与补偿

同一跳数据能算出**三个完全不同的数字**。以 X1-112 的
`joint_states_cmd → joint_states` 为例：

| 口径 | 含什么 | 实测值 |
|---|---|---|
| 整段原始 | 静止帧 + 执行滞后 + 跟随误差 | 更小（被静止段稀释） |
| 运动段原始 | 执行滞后 + 跟随误差 | **4.09°** |
| 运动段 + 时延补偿后 | **纯跟随误差 ← 判定用这个** | **0.92°** |

差的 3.2° 就是那 **77.6ms 的伺服滞后**。

> **为什么这件事重要**：不补偿就读误差，等于把「机器人慢了 78 毫秒」
> 写成「机器人偏了 4 度」。后者会让人去查机械、查标定，而问题根本不在那儿。

### 算法一：时延扫描 + 抛物线插值

在时间轴上平移其中一路信号，找残差最小的偏移量。粗扫描只能到帧间隔
（10ms），所以对极小点附近做**抛物线亚格点插值**，把分辨率提到毫秒以下。

### 算法二：用相关性给估计结果打分

**这是防止"把噪声拟合成结论"的关键设计。**

时延扫描**永远能返回一个极小点**，哪怕两路信号毫不相干。所以每个估计都要打分：

| 相关性 | 含义 | 处置 |
|---|---|---|
| < 0.30 | **估不出** | **不补偿**，lag 记 0、残差 = 原始差，报告里标灰 |
| 0.30 ~ 0.50 | 弱 | 补偿，但结论留余地 |
| ≥ 0.50 | 可用 | 正常判定 |

X1-112 各跳实测都在 0.87 ~ 1.00。

> **一个反直觉的细节**：打分要用**速度模长**做相关，不能用位置。
> 位置序列带一个很大的共同直流分量（两条手臂都在工件前方半米处），
> 直接相关恒等于 0.99，对"估得准不准"**毫无鉴别力**。
> 速度把直流去掉，剩下的才是形状。

### 验证：三条相邻跳的时延自洽

```
servo → joint_states_cmd        原始 3.57°   最优 +70.6ms   补偿后 0.268°
joint_states_cmd → joint_states 原始 4.09°   最优 +77.6ms   补偿后 0.920°
servo → joint_states（端到端）   原始 7.33°   最优 +148.3ms  补偿后 0.812°
```

**70.6 + 77.6 = 148.2 ≈ 148.3**

这是链路干净的证据（不是算法保证的恒等式）—— 端到端时延等于分段时延之和，
说明每一跳的估计都落在同一条时间轴上。

## 1.3 高频陷阱：录制空洞与逐层停发

**这是最凶险的一类问题：它会让结论完全反过来。**

X1-112 的 45 秒窗口里有**三段约 4 秒的录制空洞**。数组上相邻的两帧，
在时间上可能差 4 秒。做时延扫描时若不隔断：

```
不隔断：shift=0    → corr 0.9975
        shift=−7   → corr 0.045     ← 看起来像"平移一帧就完全不相关"
```

其实只是那几个跨空洞的巨型差分不再对齐而已 —— 它们的幅度是正常帧的上百倍，
整条相关性被它们绑架。

**`servo_joint_cmd` 更严重**：它只覆盖 47% 的时间窗口。把没发的区间前向填充成平线，
会在进出边界留下两级阶跃，实测相关性被压到 **0.036** ⇒ 这一跳被判成
"时延根本估不出来"，而实际波形吻合得很好（**真值 0.966**）。

**处置**：`timeutil.pair_segments` 把「录制空洞」和「某一层没数据」合成一套段编号，
**只配对同段内的帧**。

## 1.4 离线段怎么锚定到墙钟时间

离线 npz **没有任何时间戳**（只有隐含的 dt），必须锚到实机时间轴上才能比较。
方法是**首尾位形锚 + 单调最近点 warp**：

1. 拿离线段的**第一个位形**去 `/joint_states_cmd` 找 `max|Δ|` 最小的帧；
   末位形在它**之后**同法再找一次。
   实测两个残差是 `0.00000` / `0.00002` rad —— **不是"差不多"，是逐位吻合**：
   复现就是把这张表原样喂给控制器。所以门限可以定得很紧（`TOL_RAD = 0.02`），
   宁可漏判也不错配。
2. 段内对每个计划点取最近的记录帧，再 `maximum.accumulate` 强制索引单调，
   得到 `plan_idx → wall_time` 映射。

> ⚠ **末点必须限定在首点之后**：轨迹经常首尾相近（回到预备位），
> 不加这个约束会匹配出一段**倒着走**的区间，`time_scale` 变成负数，**而且不会报错**。

**质量指标分两路，不合并成一个数**：

- `path_resid`（逐帧最近距离）回答"**路走对了没**"
- `time_scale` / `speed_ratio` 回答"**快慢对不对**"

X1-112 实测（`organize_and_connection_start` 线束6）：

```
计划 875 点 × 10ms = 8.74s
实机 +13.94s … +21.65s = 7.69s（0.880×）
首/末位形残差     0.00000 / 0.00002 rad
逐帧路径残差 p95  0.0096 rad ≈ 0.55°
```

交叉印证：`/robot_debug_info` 在 +14.22s 报 `CONNECTION_BOTH_REPLAY`、线束名 `线束6`。

### ⚠️ 失败是常态，且必须逐条说明

X1-112 的 45 秒窗口里，**36 个离线段只命中 1 个**。

**这不是工具坏了** —— record 只覆盖报障前后几十秒，而 36 段横跨整场运行。

所以 `anchor_all` 把**没命中的段连同原因**一起返回，报告里单列一页。
静默丢掉会让人以为分析了整条 recipe。

## 1.5 推翻旧口径的发现

**这条发现让旧版的一个阈值彻底失效。**

旧版拿离线 npz 去比 `/xr_wbc/outgoing_action_goal`，在无量纲进度轴上
算出 0.179 ~ 0.205 rad 的"形状误差"，并据此把阈值定在 0.20 rad。

但那条 topic 上的是**在线重规划**的产物，**不是离线 recipe 的复现** ——
拿 A 的执行去比 B 的计划，算出来的 10° 既不是精度也不是缺陷。

正确锚定后，真实路径残差是 **0.0096 rad** —— **差两个数量级**，
旧阈值永远不会告警。

现在两条都在，名字分开了：

| 阈值 | 含义 | warn |
|---|---|---|
| `PLAN_PATH_RESID_RAD` | 执行精度 | 0.05 |
| `PLAN_VS_ONLINE_GOAL_RAD` | 重规划偏移 | 0.20 |

## 1.6 必须写进报告的六条「读数前必看」

精度报告最大的风险是**被误读**。所以报告开头固定放一份口径说明：

1. **时延占了原始误差的九成以上** —— 不补偿会读出完全不同的结论
2. **时延估不出来时必须说"估不出"** —— 而不是硬给一个数
3. **录制空洞与逐层停发必须挡掉** —— 否则结论完全反过来
4. **这不是绝对精度** —— 末端位姿是由关节编码器正运动学（FK）出来的，
   不是外部测量。**能看见**伺服跟随误差、指令与反馈的时延、链路一致性；
   **看不见**关节零位标定误差、减速器回差、连杆形变、URDF 与实物的差异。
   编码器说自己到了 0.1mm，末端实际可能差几毫米。
5. **前瞻量 ≠ 跟随误差** —— `wbc_cmd` 是笛卡尔指令层，相对下游整体**超前约 65ms**
   （含 WBC 自身前瞻），在运动速度下天然带来几十毫米的瞬时位置差。
   那是「WBC 还没走完的路」，不是误差。判断规划走得对不对要看 `plan → target`
   （实测两臂残差 **2.1 / 3.3mm**，比含 `wbc_cmd` 的两跳小一个数量级）
6. **两种时基不能混** —— `joint_states_cmd → joint_states` 两端
   `header.stamp` **逐帧严格相等**（实测 3298/3298），是同周期指令 vs 同周期编码器，
   **不含任何时间对齐猜测**；含 servo 的跳只能用 record time（servo 消息没有 header）

### 两个数据解析的坑（都会静默出错）

**① 文件名是乱码**
recipe 目录里的 npz/yaml 带中文（线束3 … 线束14），但打包时的 zip 没写
UTF-8 标志位，落盘变成 `τ║┐µ¥ƒ10`。而 `trajectory_log_metadata.yaml` 里记的是
**正确的 UTF-8 名字** —— 所以两边**不能靠字符串相等配对**。

处理：用「metadata 的 `files[]` 顺序即录制顺序 + 文件名里的 ASCII 前缀
（动作名是好的）+ 线束号」配对，**失败显式计数报出，不静默丢**。

**② npz 里的关节名是 int8 的 ASCII 拼接**（空格分隔），要按字节解 ——
`str(arr)` 出来是一串数字，会**静默得出 20 个假关节名**。

## 1.8 真机复播自动化

分析工具解决「有数据怎么看」，但**数据从哪来**是另一个问题：
需要在真机上把一条规划轨迹复播出来，同时录制，再把数据喂给分析工具。

### 目标

输入一份同事给的 mock 规划请求（yaml + 同名 npz），自动走完：

```
拆两个 yaml → 上传真机 → 起录制 → 复播 → 取回 record → 出精度报告
```

**判定口径**：能生成报告 = 成功。不看精度数值 —— 那份报告本就没有验收线
（阈值全是「单点实测 × buffer」，样本 N=1），拿它判好坏是误用。

### 为什么"拆成两个 yaml"是这样拆的

`replay_action_goal.py` 读 **action goal yaml**，从中取两样东西：

1. `request.trajectory_name` —— **只决定去哪找第二个文件**。
   WBC 的 `is_replay_mode` 判定是
   `trajectory_name.has_value() && !offline_planning.has_value()`，
   成立后走复播分支，按 `<storage_dir>/<trajectory_name>_planning.yaml` 去磁盘捞
2. `robot_state.joint_names / joint_positions` —— 复播前先 goto 到这个起始位形

**真正被逐帧执行的是 planning yaml**（WBC 从磁盘读的那份）。
action goal 里的 `frame_trajectory.points` 在复播模式下**根本不会被用**
—— 这就是 `demo_fast.yaml` 只有一个路点却也能跑起来的原因。

| 文件 | 内容 | 由谁消费 |
|---|---|---|
| `<name>.yaml` | 最小可用：`trajectory_name` + `robot_state` | `replay_action_goal.py` |
| `<name>_planning.yaml` | 完整：密集轨迹 + 速度/加速度 + 时间轴 | WBC（逐帧执行） |

**文件名是硬契约**，改名就跑不起来。

### 四个容易踩的坑

**① 两套 `MotionType` 枚举，差一个数字**

| 来源 | 枚举 | `WHOLE_BODY` |
|---|---|---|
| mock yaml（WBP 请求） | `RobotArmTrajectoryPlan.proto` | **6** |
| action goal（WBC 复播） | `ManiUnifiedTrajectory.proto` | **2** |

mock 里写的 `motion_type: 6` 是前者。**抄错不报错**，只是复播走错分支。

**② 20 个关节要去掉底盘**

mock 的关节表前 3 个是 `root_joint_x/y/theta`（底盘规划量）。
WBC 侧 `GetFilteredJointNames()` 有排除表，带底盘关节会被
`joint_names size mismatch` 拦下。输出裁到 **17 个**（腰 3 + 左臂 7 + 右臂 7）。

**③ 稀疏路点要插值成 125Hz**

mock 的 npz 只有十来个路点（实测 11 个 / 0.459s），而 WBC 按 `control_frequency`
逐周期取点执行。不插值等于要求控制器自己在 125Hz 的周期里跑完全程 ——
那不是"复现规划"。

⚠ **时间戳要先单调化**：实测 mock 的首尾各有一个 1ms 伪间隔，
非单调的结点会让 `np.interp` **静默返回错位的值**。

**④ 报告还需要 `attachment/`，不能只给两个 yaml**

`awr_analysis` 的「规划层」来自 `attachment/trajectories/recipe_<id>/*_joint.npz`。
少了它，链路**静默降级成 3 层**，「复现段」页也会空掉 ——
而这份报告的主线恰恰是「规划 vs 实际」。

### 录制：一个被误传的参数

开发给的录制命令里 `-i 1000000` 是 **segment-interval，单位秒**。
1,000,000 秒 ≈ 11.6 天，即**永不切分**。所以一次录制只产出一个 `*.record` 文件。

但**实测发现真正的行为不是这样** —— 读 C++ 源码
（`platform/cyber/record/`）才看清：

```cpp
// header_builder.h:68 编译期默认值
static const uint64_t SEGMENT_INTERVAL_ = 60 * 1000 * 1000 * 1000ULL;  // 60s

// record_writer.cc:39-49
if (header_.segment_interval() > 0 || header_.segment_raw_size() > 0) {
    path_ = file_ + ".00000";     // ← 默认走这条
} else {
    path_ = file_;                // ← 只有两个都为 0 才走这条
}
```

**判的是「有没有设过这个参数」，不是「时长有没有超过它」**。所以：

- 不传任何参数 → **每 60 秒切一个文件**（`file.record.00000` → `.00001` → …）
- 传 `-i 1000000` → 文件名**带 `.00000` 后缀**
- **正确做法**：显式传 `-i 0 -m 0`，把**两个都归零**（只归零一个不够，`||` 是或的关系）

另外**必须显式给 `-o`**：不给的话默认文件名是时间戳，而 `awr_analysis`
的布局判定要的是字面量 `file.record`。

停录制用 **SIGINT**（`pkill -INT`），**不能用 `kill -9`** —— record 尾部有索引段，
硬杀会让它不完整，`cyber_record` 打开时直接抛异常。

### 真机实测结果

**验证一：复播轨迹与 mock 一致**

```
残差 RMS 0.093°（逐点最大偏差 0.17°）—— 编码器噪声量级
```

证明「拆 yaml → 插值 → 复播」整条链路**没有引入畸变**。

**验证二：修复带来的指标提升**

| 指标 | 修复前 | 修复后 | 说明 |
|---|---|---|---|
| 全流程耗时 | 331s | **18.4s** | |
| record 时长 | 302.6s | **12.9s** | |
| 运动帧占比 | 1.9% | **13.1%** | ×6.9 |
| 控制层覆盖率 | 1.8% | **41.6%** | ×23 |

**后两项指标的含义**：修复前它们看着像「servo 通道没数据」的异常，
排查方向会指向数据源配置。实际根因是**录制被超时拖长**导致的稀释
（301 秒里只有几秒在动）。修好后 41.6% 已经接近同期 X1-112 实测的 47%。

### ⚠️ 一个我判断错两次的问题（值得记录）

关于 `-i` 参数，我先后给出过两个**错误结论**：

1. 先说"`-i 1000000` 保证不切分、文件名是 `file.record`" —— **错**，
   它只是不切*第二个*，名字照带后缀
2. 然后说"是 `-i` 造成的，去掉就行" —— **还是错**，
   真正原因是编译期默认值，去不去掉都一样

**两次都是靠读 C++ 源码 + 连真机实测才纠正的。**
这件事的教训：**当现象与文档不符时，读实现、实测，不要靠推理自洽。**

### 另一个反复出现的 bug 类型

`send_cmd` 的输出**末尾必然带 shell 提示符**（`nvidia@tegra-ubuntu:~$`）。

这个坑在同一个文件里**出现了三次**：

1. 起录制后检测文件是否出现 —— 取"最后一行"拿到的是提示符
2. 停录制后判断进程是否退出 —— `pgrep ... || echo GONE` 把退出码强制成 0，
   两种情况都返回 True（**循环第一轮就报成功、根本没等**）
3. 取复播进程 pid —— 同样取"最后一行"，拿到提示符，
   `isdigit()` 不过 ⇒ 清理逻辑静默跳过

**结论**：凡是要解析 `send_cmd` 输出的地方，**都得用标记定位，不能用行位置**。

# 二、测试数据记录服务

## 2.1 业务场景

测试人员在产线旁对线束做插接测试，结果需要记录：

```
        ┌─────────────┐
前端 ──►│ FastAPI 服务 │──► 飞书多维表格（按设备分散在多张表）
        └──────┬──────┘
               │
Jira / 飞书项目 ──┘  缺陷单自动关联回填到对应记录行
```

**核心约束**：飞书多维表格有两个硬上限 ——
**单 Base 100 张表**、**单表 20,000 条记录**。而测试记录是持续追加的。

## 2.2 按设备 + 阶段动态路由

**问题**：每台设备（190+ 台）对应一张飞书表，而且每个测试阶段（`FAE_HEBI` /
`测试_HEBI` / `集成_HEBI`）还有各自的表。硬编码映射表不可维护。

**方案**：请求里带 `设备号` + `测试阶段_地点`，服务**实时查表名映射**定位目标表：

```python
# AIO 模式：前缀匹配
prefix = f"{num}#{base}_AIO"          # 例：271#测试_HEBI_AIO
# 匹配规则：名字正好等于它，或以 prefix + "_" 开头
```

**收益**：新建设备表**无需改代码**，服务自动发现。

**代价 / 踩到的坑**：
- 表名拼错或**表还没建** ⇒ 路由失败 ⇒ 写入失败（且回退路径用的静态映射
  ID 可能也已失效，双重失败）
- 前缀多于一张表匹配 ⇒ 报"无法确定目标"（**这是保护，不是 bug**）

## 2.3 飞书多维表格的字段适配

飞书 API 的字段类型写法和读取形态都比较绕，实际处理过的：

| 类型 | 写入 | 读取 |
|---|---|---|
| 日期 | 毫秒时间戳（`datetime.strptime(...).timestamp() * 1000`） | 毫秒时间戳 |
| 文本 | 字符串 | **分段数组** `[{"type":"text","text":"7"}]` |
| 单选/多选 | 值必须在选项集内 | 同左 |
| 人员 | 邮箱 → 批量解析 open_id | 用户对象 |
| URL | `{"link": ..., "text": ...}` | 同左 |

**三个静默失败的场景**（都会丢数据但不报错）：

| 情况 | 结果 |
|---|---|
| 列**不存在** | 静默丢弃 + 在 `missing_fields` 里列出 |
| 列存在但**选项集空**（AIO 模式禁扩选） | 静默丢弃 + 警告 |
| 列存在但**值不在选项里** | 静默丢弃 + 警告 |

> **实测数据**：某设备 312 次写入，**312 次「设备号」字段全部被丢弃**
> （100% 命中）。根因是该表的「设备号」单选字段**选项集为空**，
> 而 AIO 模式禁用了自动扩选（避免 1254062 错误）。
> 记录进表了，但那一列是空的 —— **没有任何一处报错**。

## 2.4 写入去重（应对 APP 重试）

**背景**：APP 侧给提交接口加了两轮重试来扛网络波动。但重试解决不了一种情形：

```
请求已到达 → 飞书已写入 → 返回包在回程丢失 → APP 超时 → 重试
```

现场实测：同一批数据在 3 秒内写了 4 次，飞书表里出现**三条一模一样的记录**
（`16:19:23` 同线束同时间）。

### 设计

**去重键 = `日期 + 时间 + 线束号`**
同一条线束在同一时刻只会被测一次。

**为什么不用全字段比较**：重试期间人可能已经在飞书里补了某列
（比如补了「问题描述」），那时全字段比较会判成"不同"而写入重复行。

**两层去重**：

1. **批内**：同一请求里如果有重复行，先去掉（不花 API 调用）
2. **跨请求**：查目标表里该日期已有的记录，命中就跳过

### ⚠️ 最关键的一行

`FeishuClient.search_records` 默认带 **5 分钟 TTL 的类级缓存**。
而 APP 的重试通常发生在**几十秒内** —— **正落在缓存窗口里**。

用缓存结果去重，会读到"写入之前"的快照、查不到刚落库的那条 ⇒
**重复照样写进去，去重形同虚设**。

所以去重查询**必须** `use_cache=False`。有测试专门断言这一条。

### 安全取向：宁可漏去重，不可错去重

| | 后果 |
|---|---|
| 漏去重 | 多一条重复记录，人工删掉即可 |
| **错去重** | **真实记录被丢弃，数据永久不存在，而且没人会发现** |

所以凡是"键不完整 / 查询失败"的行，**一律放行写入**，不做去重。

## 2.5 缺陷单自动回填

**需求**：Jira / 飞书项目里新建的缺陷单，自动关联到飞书表里对应的测试记录行。

**匹配逻辑**（三重）：

```
设备号（从缺陷单标题/字段解析）
+ 线束号（从标题正则提取）
+ 时刻（±600 秒容差）
```

**匹配到之后**把缺陷链接**追加**到该行的「问题链接」列
（一条记录可挂多个缺陷单）。

**幂等**：同一缺陷单重复投递（webhook 会重投）不会重复追加 ——
先检查该行的 TC 编号列表里是否已存在。

**无匹配时**明确记录跳过原因，不静默丢：

```
TC 回填跳过 7136741028：信息不全（设备号=271 线束号=? 问题时刻=...）
TC 回填跳过 7136688539：无匹配记录（设备=111 线束=8 时刻=... 容差±600s）
TC 回填跳过 7136449710：没有设备 277 的数据表
```

## 2.6 一个影响归档设计的耦合点

「回填」和「数据归档」是**互相耦合**的 —— 归档会删掉的记录，
可能正是回填还要回源表查的。

梳理后发现两个回填函数的行为不同：

| 函数 | 时间窗口 | 影响 |
|---|---|---|
| `run_backfill` | **扫全表，无时间窗口** | 理论上会回写任意老记录；但它拉哪些缺陷单由 `days` 参数决定（默认 1），所以实际不会匹配到很久以前的记录（时刻差远超 ±600s 容差） |
| `reconcile_moment` | **只处理最近 7 天**创建的行 | 保留期 > 7 天即可让它不再去找被删的记录 |

**结论**：归档保留期下限定 **10 天**（配置里强制 `> 7`），
并把这个耦合关系写进两个仓库的代码注释，避免两边逻辑漂移。

> ⚠️ 这里的判断我**修正过一次**：最初写的是"回填窗口是 7 天"，
> 读代码后发现 `run_backfill` 实际**扫全表、没有时间窗口**，
> 7 天是 `reconcile_moment` 的参数。两者混为一谈会把风险判断错。

# 三、贯穿两个项目的经验

## 3.1 静默失败是主要敌人

两个项目里最危险的问题都是**不报错的那种**：

| 问题 | 表现 |
|---|---|
| 录制空洞不隔断 | 相关性被压到 0.03，一次完好的执行被误判成"数据不可用"（真值 0.966） |
| 时延估不出硬给数 | 把"机器人慢了 78ms"写成"机器人偏了 4°" |
| 单选字段选项集空 | 312 次写入、312 次字段被丢，零报错 |
| 列不存在 | 静默丢弃，只在 `missing_fields` 里露出 |
| `MotionType` 抄错 | 不报错，复播走错分支 |
| npz 关节名按 str 解 | 静默得出 20 个假关节名 |
| 去重查询走缓存 | 部署了等于没部署 |
| 锚点末点不限定时序 | `time_scale` 变负数，**不报错** |

**应对的原则**：

- 拿不准时**偏保守**（时延估不出就不补偿；去重键不完整就放行写入）
- **失败要带原因**（`anchor_all` 把没命中的段连同原因返回；回填跳过打日志）
- 关键行为**写测试钉住**（`awr_analysis` 57 个 + 复播离线自检 8 个 + 去重 25 个）

## 3.2 物理量的正确解读

同一组数据，口径不同会得出**相反**的结论：

- 「原始误差 4.09°」vs「补偿后 0.92°」 —— 差的 3.2° 是**滞后不是误差**
- 「路径残差 0.0096 rad」vs「旧口径 0.20 rad」 —— 后者是**拿 A 的执行比 B 的计划**
- 「前瞻量 65ms 的位置差」vs「跟随误差」 —— 前者是**还没走完的路**
- 「整段平均」vs「运动段」 —— 静止段会**稀释**指标

**方法**：每个数字都要能回答「它含什么、不含什么」，
并把口径写进报告让读者也能判断。

## 3.3 排障方法：现象与文档不符时读实现

多次遇到**文档/常识与实际实现不符**：

| 以为 | 实际 | 怎么发现 |
|---|---|---|
| `-i 1000000` ⇒ 文件名是 `file.record` | 带 `.00000` 后缀 | 读 C++ 源码 + 真机 `ls` |
| `-i` 是元凶 | 是编译期默认值 `SEGMENT_INTERVAL_ = 60s` | 同上（**第一次判断是错的**） |
| `pgrep \|\| echo GONE` 能判断进程存活 | 退出码被强制成 0，恒为真 | 真机实测循环第一轮就退出 |
| `str(npz 关节名)` 能拿到名字 | int8 ASCII 拼接，要按字节解 | 读出来是数字串才发现 |
| 保留期 7 天够 | `run_backfill` 无时间窗口，7 天是另一个函数的参数 | 读代码 |

**教训**：**推理自洽不等于正确**。该读源码就读源码，该实测就实测。
